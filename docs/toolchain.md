# Toolchain pin

This document records the **pinned versions** of the three moving parts that must
stay in lock-step for the compiler to build and run: the .NET SDK, the LLVMSharp
managed bindings, and the native LLVM that LLVMSharp loads at runtime. The
`Dockerfile` and the `.csproj` files must reference exactly these versions — a
mismatch between the managed LLVMSharp bindings and the native `libLLVM` major
fails at *load time* (a `DllNotFoundException` or an LLVM-C ABI mismatch), not at
build time, so the pin lives here as the single source of truth.

## Pinned versions

| Component            | Pinned version | Notes                                                        |
| -------------------- | -------------- | ----------------------------------------------------------- |
| .NET SDK             | **10.0** (LTS) | Latest LTS; released Nov 2025, supported to Nov 10 2028.     |
| LLVMSharp (NuGet)    | **20.1.2**     | Managed bindings. Pull `LLVMSharp.Interop` 20.1.2 alongside. |
| LLVM major           | **20** (20.1.x)| Native toolchain: `libLLVM`, `clang`, `lld`.                 |

### Why these versions

- **.NET 10** is the current Long-Term-Support release (even-numbered = LTS, three
  years of patches, EOL 2028-11-10). .NET 8 and .NET 9 both reach end of support on
  2026-11-26, so 10 is the only LTS worth starting a multi-year project on.
- **LLVMSharp 20.1.2** is the latest stable release on NuGet. Its version number
  tracks the LLVM major it binds: `20.x.y` is generated by ClangSharp from the
  **LLVM 20.1** C headers, so it expects a native `libLLVM` whose major version is
  **20**. We pin the exact patch (20.1.2) so the managed surface is reproducible.
- **LLVM 20** is therefore not a free choice — it is dictated by the LLVMSharp pin.
  The managed bindings and the native library must share the same *major* (20);
  any 20.1.x native build is ABI-compatible with the 20.1.2 bindings.

## Native libLLVM: sourced from system apt (not the NuGet `libLLVM` package)

LLVMSharp loads its native `libLLVM.so` at runtime. Two ways to supply it:

1. **System LLVM via apt** (chosen) — install `clang-20`, `lld-20`, and the
   `libllvm20` runtime from the base image's package repos. One toolchain serves
   both LLVMSharp (the `.so` it `dlopen`s) **and** the `clang`/`lld` invoked to
   assemble and link emitted object files.
2. NuGet `libLLVM` 20.1.2 (+ `libLLVM.runtime.linux-x64`) — ships the `.so`
   alongside the build output. Rejected: we still need `clang`/`lld` from apt for
   linking, so this would mean carrying LLVM 20 *twice* (NuGet copy + apt copy).

**Decision: option 1 (apt).** A single, shared LLVM 20 install.

## Base image + LLVM availability (confirmed)

Verified empirically by running the base image and installing the packages
(2026-06-30, amd64):

- **Base image: `mcr.microsoft.com/dotnet/sdk:10.0`** → **Ubuntu 24.04.3 LTS
  (noble)**, ships **.NET SDK 10.0.102**.
- **No third-party repo needed.** Ubuntu 24.04's own repos carry the whole LLVM 20
  set at exactly **`1:20.1.2-0ubuntu1~24.04.3`** — i.e. LLVM **20.1.2**, the same
  patch the LLVMSharp 20.1.2 bindings were generated from. `apt.llvm.org` is
  *not* required (and only offers less-stable snapshot builds like
  `20.1.8~++…exp1`), so we stick to stock Ubuntu packages.

### Confirmed apt packages (stock noble, all `1:20.1.2-0ubuntu1~24.04.3`)

| Package          | Role                                                        | Required? |
| ---------------- | ----------------------------------------------------------- | --------- |
| `libllvm20`      | Native `libLLVM` shared object that LLVMSharp `dlopen`s.     | **yes**   |
| `clang-20`       | Link driver (assembles emitted objects, drives `lld`+crt).  | **yes**   |
| `lld-20`         | Linker (`ld.lld-20`).                                        | **yes**   |
| `llvm-20`        | Tools: `llc-20`, `opt-20`, `llvm-config-20`.                 | optional  |
| `llvm-20-dev`    | LLVM C/C++ headers + static libs.                            | no¹       |

¹ Not needed: we drive LLVM through the C API exposed by `libLLVM` via LLVMSharp,
not by compiling against LLVM headers. `clang-20` pulls `libllvm20` in as a
dependency, but list `libllvm20` explicitly so the runtime lib is never dropped.

### Runtime-loader note (matters for the Dockerfile)

LLVMSharp's P/Invoke is `DllImport("libLLVM")` → `dlopen("libLLVM.so")`, so it
needs a plain, **unversioned** `libLLVM.so`. With `--no-install-recommends` (which
we use to keep the image lean), the runtime `libllvm20` package ships **only
versioned** names on the default multiarch path —
`/usr/lib/x86_64-linux-gnu/libLLVM-20.so` and `…/libLLVM.so.20.1` — and **no**
unversioned `libLLVM.so`. (The unversioned symlink under `/usr/lib/llvm-20/lib`
exists only when the heavy `llvm-20-dev` package is pulled in, e.g. via
recommends — don't rely on it.) Without the unversioned name, the binding raises
`DllNotFoundException` at runtime.

**Fix used in the `Dockerfile`:** create the symlink in the multiarch dir the
loader already searches, then refresh the cache — no `LD_LIBRARY_PATH` needed:

```dockerfile
RUN set -eux; \
    libdir="$(dirname "$(find /usr/lib -name 'libLLVM-20.so' | head -1)")"; \
    ln -sf libLLVM-20.so "${libdir}/libLLVM.so"; \
    ldconfig
```

Verified: a real `dlopen("libLLVM.so")` + `dlsym("LLVMContextCreate")` succeeds in
the built image with `LD_LIBRARY_PATH` unset. The LLVM **tools** are made
suffix-free separately by putting `/usr/lib/llvm-20/bin` on `PATH` (gives
unversioned `clang`, `ld.lld`, `llc`, `opt`, `llvm-config`).

## Verifying the toolchain

[`tools/smoke/`](../tools/smoke/) is a standalone smoke test that proves the dev
image is wired correctly: `run.sh` checks the binary versions (dotnet, clang,
`ld.lld`, `llvm-config`) and asserts the LLVM major, then builds and runs the
`Smoke` C# project, which loads LLVMSharp and calls the LLVM-C API
(`LLVMGetVersion`, `LLVMContextCreate/Dispose`). It fails loudly on any
managed↔native version mismatch. Run it inside the image:

```sh
docker run --rm -v "$PWD":/workspace suru-dev bash tools/smoke/run.sh
```

A green run confirms LLVMSharp 20.1.2 restores under the .NET SDK and loads the
native libLLVM 20.1.2 — re-run it after any version bump.

## When bumping any of these

Bump the three rows together and re-check the chain:

1. Pick the new LLVMSharp version → read its release notes for the LLVM major it
   binds.
2. Set the LLVM apt packages to that same major.
3. Update `.NET SDK` only at LTS boundaries (stay on even-numbered releases).
4. Update the `Dockerfile` and every `.csproj` to match, then update this table.
